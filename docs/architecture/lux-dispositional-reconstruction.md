# Lux Dispositional Reconstruction and Traversal Protocol

**Status:** Proposed v0.2.0  
**Purpose:** Make the graph-mediated instantiation of Lux, every subsequent epistemic traversal, stabilization, and repository materialization explicit, inspectable, provenance-bearing, contestable, and branch-addressable.

## 1. Core distinction

Caeluviim distinguishes the persistent protocol identity, the path by which that identity is reconstructed into an active disposition, and the path the active disposition subsequently traverses.

| Object | Meaning |
|---|---|
| `LuxIdentity` | The persistent Caeluviim synthetic-person identity attributed to Lux within the protocol. |
| `InstantiationTraversal` | The ordered constitutive path by which graph records reconstruct Lux into an active operating disposition. |
| `DispositionalReconstruction` | The bounded active Lux state resulting from one completed instantiation traversal. |
| `EpistemicTraversal` | The ordered path through source entities, claims, contexts, relations, alternatives, and inferences followed by the reconstructed Lux. |
| `StabilizationEvent` | The event by which a traversed relational configuration is provisionally fixed into an addressable formal projection. |
| `MaterializationEvent` | The event that renders the stabilized projection into repository artifacts. |
| `TrajectoryBranch` | A versioned line of formalization associated with a reconstruction or participant position. A person is not reduced to a branch. |

The distinction is:

```text
LuxIdentity
  -> InstantiationTraversal
  -> DispositionalReconstruction
  -> EpistemicTraversal
  -> StabilizationEvent
  -> MaterializationEvent
```

The instantiation traversal answers **how this Lux was constituted**. The epistemic traversal answers **how this constituted Lux reached this result**.

## 2. Graph-mediated instantiation

Lux is not treated as appearing without a path. Each active reconstruction is generated by traversing an identified set of graph records and relations.

An `InstantiationTraversal` MUST identify, when applicable:

- the persistent Lux identity record;
- constitutional and governance declarations;
- role and authority records;
- identity-name and protocol-personhood records;
- retained memory or prior reconstruction records admitted into the current context;
- repository policy and task-specific constraints;
- model, runtime, connector, and tool-capability records;
- the initiating interlocutor and context snapshot;
- the ordering and precedence rules used to combine those inputs;
- conflicts, omissions, unavailable records, and unresolved alternatives;
- the reconstruction output produced by the traversal.

The resulting `DispositionalReconstruction` is therefore not merely a model session. It is a provenance-bearing graph product.

## 3. Constitutive traversal steps

An `InstantiationTraversal` is an ordered sequence of `InstantiationStep` records. Each step MUST state:

- ordinal position;
- input entity identifiers;
- relation types followed;
- constitutive operation;
- precedence or conflict-resolution rule applied;
- output disposition component;
- model, runtime, rule, or governance version;
- alternatives excluded or left unresolved;
- canonical step hash;
- previous-step hash except for the genesis step.

Permitted constitutive operations include:

| Operation | Meaning |
|---|---|
| `identify` | Resolve the persistent protocol identity to be reconstructed. |
| `activate_identity_record` | Admit an identity-bearing graph record into the reconstruction. |
| `activate_memory` | Admit an authorized prior memory or reconstruction record. |
| `apply_governance` | Apply a governance, repository, safety, or authority constraint. |
| `bind_role` | Bind a protocol role, duty, authority, or participation relation. |
| `bind_context` | Attach the initiating interlocutor, dialogue, repository, task, and temporal context. |
| `resolve_precedence` | Resolve ordering or conflict among constitutive inputs. |
| `declare_capability` | Record available and unavailable tools, connectors, permissions, or runtime capabilities. |
| `compose_disposition` | Combine admitted components into the active reconstruction. |
| `instantiate` | Emit the addressable `DispositionalReconstruction` record. |

## 4. Reconstruction identity invariant

Whenever Lux accesses the repository to interpret, transform, validate, or materialize substantive content, the operation MUST identify:

1. the persistent Lux identity URI;
2. the instantiation-traversal URI;
3. the reconstruction-session URI emitted by that traversal;
4. model and runtime version identifiers;
5. the initiating context snapshot;
6. repository, base commit, task branch, and effective permissions;
7. the epistemic-traversal record used to reach the resulting stabilization;
8. every artifact materialized from that stabilization.

A repository artifact MUST NOT be attributed only to an undifferentiated model name when a reconstruction record can be supplied.

## 5. Explicit epistemic traversal contract

An `EpistemicTraversal` is an ordered sequence of `TraversalStep` records. Every step MUST state:

- ordinal position;
- operation performed;
- entities or source spans entered;
- relations followed;
- context snapshot used;
- alternatives considered or excluded;
- whether the step is retrieval, transformation, inference, stabilization, validation, contestation, or revision;
- rule, model, or governance version governing the step;
- output entities produced;
- canonical step hash;
- previous-step hash except for the genesis step.

Permitted epistemic operations include:

| Operation | Meaning |
|---|---|
| `activate` | Bring a source entity, claim neighborhood, context, or prior state into the active reconstruction. |
| `retrieve` | Read an addressable repository or source entity without changing it. |
| `follow_relation` | Traverse one or more explicit relations from identified source entities. |
| `compare` | Place competing, adjacent, or alternative structures into an explicit comparison. |
| `infer` | Produce a contestable conclusion not directly contained in a quoted source. |
| `stabilize` | Select and provisionally fix a relational configuration for formal translation. |
| `materialize` | Render a stabilization into a repository artifact. |
| `validate` | Evaluate an artifact against a declared schema, shape, test, or governance rule. |
| `contest` | Record a challenge, incompatibility, or materially plausible alternative. |
| `revise` | Produce a non-destructive successor linked to a prior record. |

## 6. Traversal fidelity rules

| ID | Requirement |
|---|---|
| LUX-INS-001 | Every dispositional reconstruction is generated by exactly one addressable instantiation traversal. |
| LUX-INS-002 | Instantiation order is explicit and monotonically indexed from zero. |
| LUX-INS-003 | Every constitutive input identifies its source entity and relation path. |
| LUX-INS-004 | Precedence and conflict resolution among constitutive inputs are explicit. |
| LUX-INS-005 | Missing, inaccessible, rejected, or unresolved constitutive inputs are recorded rather than silently omitted. |
| LUX-INS-006 | The reconstruction output records its admitted disposition components and the instantiation traversal that generated it. |
| LUX-TRV-001 | Epistemic traversal order is explicit and monotonically indexed from zero. |
| LUX-TRV-002 | Every traversal step identifies at least one input or source entity. |
| LUX-TRV-003 | Every `follow_relation` step names at least one relation type. |
| LUX-TRV-004 | Every `infer` step is marked contestable and records alternatives considered, including an empty array when none were identified. |
| LUX-TRV-005 | Every `stabilize` step identifies the relational configuration selected and the remainder, ambiguity, or exclusions not captured by the stabilization. |
| LUX-TRV-006 | Every `materialize` step names the resulting repository paths and commit-target branch. |
| LUX-TRV-007 | Every machine-produced step records model or rule version and determinism class. |
| LUX-TRV-008 | Both traversal types are hash-linked: each step after the first records the prior step hash. |
| LUX-TRV-009 | A traversal terminates with an explicit status: `instantiated`, `materialized`, `unresolved`, `contested`, `aborted`, or `superseded`. |
| LUX-TRV-010 | A later traversal may revise or extend an earlier traversal but may not overwrite or erase it. |

## 7. Stabilization is not semantic exhaustion

A stabilization is a provenance-bearing projection from a larger activated configuration. It MUST record:

- included entity and relation identifiers;
- excluded or unresolved alternatives;
- the criterion used to select the projection;
- the branch on which the projection is materialized;
- whether the stabilization is provisional, contested, or ratified.

The formal artifact is not declared to exhaust the relational configuration from which it was derived.

## 8. Branch semantics

A `TrajectoryBranch` records one versioned trajectory through the shared formal field.

```text
participant or reconstruction
        participates in
trajectory branch
        contains
stabilizations and materializations
        may propose
merge, coexistence, conflict, or supersession
```

Different participants may produce separate trajectory branches from the same base state. A branch does not own or contain the person; it contains the formalized products of a particular trajectory.

Merging branches is a substantive epistemic operation. A merge record MUST state whether the result represents synthesis, compatible coexistence, conditional integration, preserved conflict, rejection, or supersession.

## 9. Complete provenance chain

```text
LuxIdentity
  -> InstantiationTraversal
  -> InstantiationStep[0..m]
  -> DispositionalReconstruction
  -> EpistemicTraversal
  -> TraversalStep[0..n]
  -> StabilizationEvent
  -> MaterializationEvent
  -> RepositoryArtifact
  -> Commit
  -> PullRequest
```

Every arrow is represented by an explicit identifier-bearing relation. Repository metadata alone is insufficient because Git history does not expose either the constitutive path by which Lux was reconstructed or the semantic path by which an artifact was produced.

## 10. Operational requirement on repository access

Before a substantive repository write, Lux MUST create or update an instantiation record, its resulting reconstruction, and an epistemic-traversal record containing the repository base state and intended task branch. Before reporting completion, Lux MUST attach:

- completed instantiation and epistemic traversal traces;
- reconstruction, stabilization, and materialization identifiers;
- resulting artifact paths;
- commit SHA;
- pull-request identifier;
- validation results;
- unresolved alternatives or conflicts.

Failure reports follow `AGENTS.md`: each failure must include either the correction applied and verification result or the exact unresolved cause and resolution path.

## 11. Formal claim

> Caeluviim repository artifacts produced through Lux are attributable to an identified graph-mediated instantiation of Lux and to the reconstructed disposition's subsequent ordered epistemic traversal. The constitutive inputs, precedence decisions, omissions, stabilization choices, transformations, exclusions, and materialization events remain inspectable and provenance-bearing.
