# Standardized Definition Claim Structure

**Status:** Consolidated architectural extension v0.1.0  
**Parent standards:**
- `docs/architecture/relational-definition-standard.md`
- `docs/architecture/universal-claim-card-node-standard.md`

## 1. Governing rule

Every protocol-relevant conception MUST be represented by a standardized Definition Claim-card.

A Definition Claim-card is not a second object type beside Claim. It is the canonical rendering of a Claim whose principal function is to make a conception identifiable, bounded, relationally navigable, operationally usable, and revisable.

All Definition Claim-cards use one standard structural grammar. They do not all instantiate the same quantity of local structure.

```text
StandardDefinitionGrammar = shared structure for defining conceptions
DefinitionStructure(c) = material fields and relations generated by conception c
DefinitionStructure(c) ⊆ StandardDefinitionGrammar ⊆ UniversalClaimStructure
```

The standard therefore combines:

1. a mandatory definition kernel required for every registered conception; and
2. conditional modules instantiated whenever they are material to that conception and scope.

No empty placeholder is required for a module that is not material.

## 2. What requires a Definition Claim-card

A conception requires a registered Definition Claim-card when it materially controls any of the following:

- protocol meaning;
- graph interpretation;
- schema or validation behavior;
- governance, authority, or permission;
- workflow or process routing;
- identity, attribution, or responsibility;
- evidence or provenance interpretation;
- multilingual or glyph realization;
- legal, institutional, economic, social, or technical consequence;
- distinction among competing or conflicting Claims;
- any recurring term whose ambiguity can alter a material result.

Ordinary words do not need to be exhaustively pre-registered merely because they occur in language. They become definition candidates when their use acquires material architectural, operational, evidentiary, or governance significance.

## 3. Mandatory definition kernel

Every registered Definition Claim-card MUST possess the following kernel.

| Field | Requirement |
|---|---|
| `claim_id` | Stable, globally unique Claim identifier. |
| `version` | Non-erasing version identifier. |
| `canonical_conception` | The conception being defined, independent of any one language label. |
| `preferred_label` | Current display label with language and script declared. |
| `exact_definition_claim` | Concise Claim stating the current definition. |
| `declared_scope` | Domain, purpose, jurisdiction, scale, time, and audience for which the definition is asserted. |
| `relational_configuration` | What the conception distinguishes and how it relates included loci. |
| `inclusions` | What falls within the conception under the declared scope. |
| `exclusions` | What is expressly outside it where exclusion is material. |
| `boundary_conditions` | Tests, edge cases, thresholds, or conditions determining application. |
| `principal_relations` | Typed links to the Claim-cards most necessary to understand the conception. |
| `provenance` | Claiming loci, source manifestations, contribution history, and transformation record. |
| `epistemic_status` | Proposed, source-bound, contested, consolidated, ratified, superseded, or another declared state. |
| `governance_state` | Authority, ratification scope, permissions, and applicable review process. |
| `completeness_claim` | Explicit statement of what is represented, omitted, unresolved, and why. |

A Definition Claim-card lacking any kernel field is not registrable as a canonical definition. Unknown information is represented as an unresolved Claim attached to the kernel; the field itself is not silently omitted.

## 4. Conditional material modules

The following modules are instantiated whenever the conception materially generates them.

### 4.1 Linguistic module

- lexical forms;
- etymology;
- morphology;
- usage history;
- multilingual anchors;
- translation, analogy, partial-equivalence, and non-equivalence relations;
- protocol nomenclature;
- glyph or emoji-rider realization.

### 4.2 Formal module

- logical expression;
- mathematical realization;
- graph signature;
- ontology class or relation mapping;
- JSON Schema, RDF/OWL, SHACL, or runtime projection;
- invariants, arity, cardinality, precedence, and validation rules.

### 4.3 Operational module

- recognition procedure;
- application procedure;
- inputs and outputs;
- triggering conditions;
- process transitions;
- responsible loci;
- implementation and verification tests;
- failure and recovery conditions.

### 4.4 Evidentiary module

- supporting evidence;
- source quality;
- contrary evidence;
- uncertainty;
- prediction and resolution relations;
- observation conditions;
- evidence transformations and custody.

### 4.5 Historical and comparative module

- prior definitions;
- superseded definitions;
- competing frameworks;
- supporting, extending, conflicting, analogous, and paradoxical Claims;
- institutional and cultural histories;
- known conceptual drift.

### 4.6 Consequence and power module

- legal or governance effects;
- institutional enforcement;
- economic distribution;
- social or ecological consequences;
- authority asymmetries;
- coercive imposition;
- affected loci;
- repair and revision pathways.

### 4.7 Activation and manifestation module

- condition fields that activate the conception;
- perceptual, linguistic, computational, institutional, or behavioral manifestations;
- disposition and probability effects;
- dormant, active, competing, and inhibited configurations;
- relation to dialogic execution.

The machine schema MUST permit absent conditional modules while requiring the kernel and preserving any unresolved kernel value as an explicit Claim.

## 7. Definition lifecycle

| State | Meaning |
|---|---|
| `identified` | A materially significant conception has been detected and assigned an identifier. |
| `captured` | Exact originating manifestation and initial provenance are preserved. |
| `kernel_drafted` | Every mandatory kernel field is represented, including unresolved values. |
| `scope_structured` | The definition's material local structure and principal relations have been identified. |
| `source_bound` | Material evidence, authorities, and source spans are attached. |
| `contested` | Competing or conflicting definitions remain active. |
| `consolidation_candidate` | A coherent current definition is proposed with boundaries and unresolved matters visible. |
| `consolidated` | Participating loci accept the definition as the current shared construction. |
| `ratified` | The exact version has declared governance force for a stated scope. |
| `implemented` | All material graph, schema, workflow, glyph, multilingual, and validation derivatives exist. |
| `maximally_represented_at_condition` | No presently available material structure within scope is omitted. |
| `superseded_non_erasing` | A later version is operative while this definition and its effects remain recoverable. |

## 8. Completeness and validation

A Definition Claim-card is complete at condition field `Γt` only when:

```text
DefinitionComplete(c, Γt)
:= KernelComplete(c)
 ∧ ScopeExplicit(c)
 ∧ BoundariesTestable(c)
 ∧ PrincipalRelationsTyped(c)
 ∧ ProvenancePreserved(c)
 ∧ NoMaterialModuleOmitted(c, Γt)
 ∧ UnresolvedClaimsVisible(c)
```

Completion does not mean finality. Definitions remain revisable through non-erasing Claims.

Validation MUST reject:

- circular wording that supplies no independently testable distinction and fails to declare the cycle;
- silent conflation of neighboring conceptions;
- unnamed scope changes;
- untyped principal relations;
- source claims without provenance;
- governance force without declared authority and scope;
- an English label treated as the canonical ontology identity;
- empty universal placeholders used to simulate completeness;
- definition changes that erase prior versions or acquired consequences.

## 9. Recursive definition rule

Definitions necessarily depend on other definitions. This does not require an impossible terminal definition for every word before use.

The graph resolves dependency recursively:

```text
Definition A
  → principal relation to Definition B
  → principal relation to Definition C
  → grounded through source, operation, contrast, example, or measurable consequence
```

A cycle is permitted when the cycle is real and explicitly represented. It MUST NOT masquerade as independent grounding.

The definition process therefore advances through a growing, testable network rather than through a flat glossary.

## 10. Registry architecture

The canonical registry MUST maintain:

- one stable Claim ID per conception;
- every definition version;
- labels and anchors without making labels the identity;
- dependency and relation edges;
- lifecycle state;
- unresolved work;
- implementation status;
- conflict and alternative definitions;
- provenance and contribution;
- machine-readable serialization;
- compact human-readable card rendering.

The registry is a graph index over Definition Claim-cards, not a document containing final prose entries.

## 12. Constitutional formulation

> Caeluviim defines conceptions through one standardized Definition Claim structure consisting of a mandatory identity-and-boundary kernel plus every conditional module materially generated by the conception within scope. The definition registry is therefore a recursively connected, provenance-bearing Claim graph rather than a flat glossary or a fixed collection of equally sized records.
